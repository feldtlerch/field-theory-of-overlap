# ADR 046: Registered HTML block gaps · `rec:adr:046-registered-html-block-gaps`

**Decision (Statement)** · `dec:documents:registered-html-block-gaps`

Native conversion may precede the HTML emitter for an admitted inline kind while the development document has a plan-recorded, unlinked notice at that block. Every such HTML block gap belongs in `registry/html-block-gaps.json`, identified by document, unit, zero-based block position in the checked document plan, and unsupported inline kind; multiple unsupported kinds in one block require separate rows. The register uses canonical JSON bytes and kebab-case field names under `dec:serialization:strict`, so duplicate keys and other non-canonical spellings refuse. The product-only `paper check-registered-html-gaps --built` command compares the ordered register with the plan's complete gap inventory, so an added, removed or changed gap refuses; it then requires all release parts other than HTML block gaps to pass and requires the ordinary release refusal at HTML block gaps to name the registered inventory. `paper check --release` still refuses any HTML block gap. The register must be empty before a version is released.

**Reasons (Why)** · `arg:documents:registered-html-block-gaps-reasons`

The native source and PDF passage can be verified before the corresponding HTML inline emitter exists. An explicit, exact inventory permits that development sequence without representing a missing screen passage as complete. Matching the checked plan prevents a newly missing passage from becoming an unnoticed exception, and the ordinary release refusal preserves the complete-document boundary.

**Declined (Alternatives)** · `arg:documents:registered-html-block-gaps-declined`

Treating the notice as released content would break the screen contract. Omitting a converted unit until HTML catches up would delay the independent PDF and Markdown evidence. A free-form exception list would not detect a changed block or inline kind.

**Consequences (Accepted)** · `arg:documents:registered-html-block-gaps-consequences`

The development product test is green only when the register exactly matches the plan and every other release part passes. The release command and its acceptance boundary are unchanged. The register is temporary evidence of incomplete HTML, not a substitute for the emitter, its recovery, or independent screen acceptance. Its rows disappear as emitters are added, and a version release requires an empty register.
