**Reasons (Why)** · `arg:documents:html-mathematics-reasons`

Using the paper's mathematics face keeps the shapes of its letters and operators related to the prose surrounding them. Font metrics can guide several engines without requiring identical pixels: the OpenType MATH table supplies font-specific layout data, not a unique layout algorithm. Native MathML keeps mathematical structure available to browser accessibility and selection facilities and avoids shipping a second client-side layout program. Generation-time derivation preserves deterministic document bytes while leaving the browser responsible for pixels and line layout.

Documentation read on 2026-11-21 supports this route, not an assertion of formula-by-formula compatibility. [MathML Core's published snapshot](https://www.w3.org/TR/2025/CR-mathml-core-20250624/) is dated 2025-06-24; [current browser documentation](https://developer.mozilla.org/en-US/docs/Web/MathML) reports MathML across Blink, Gecko and WebKit. [The upstream font distribution](https://ctan.org/tex-archive/fonts/tex-gyre-math) identifies Pagella Math as an OpenType mathematics font under the GUST Font License. The checked notation adapter already uses pinned KaTeX with strict errors and untrusted input; using its MathML output avoids adding another TeX grammar. Bounded output admission and retained observation with the exact embedded file supply the evidence that a parser alone cannot provide.

**Declined (Alternatives)** · `arg:documents:html-mathematics-declined`

Changing the CSS family of KaTeX's positioned HTML does not recompute its font metrics and is not a Pagella layout route. KaTeX's own faces are a possible measured fallback, but introduce a different mathematical appearance beside Pagella prose on every affected line. MathJax 4 provides a Pagella-derived font package and server-side HTML/CSS or SVG; it does not make an arbitrary OpenType file into that package by naming it in CSS. Adding its parser, font data and layout system before a native-browser failure is established duplicates work already supplied by the strict notation adapter and the browser. TeX-to-SVG can use the exact paper font, but introduces another conversion toolchain and needs separate evidence for selectable text, accessibility and link regions. Browser-time library execution adds delivery and resource-loading obligations without improving the authority of the source. Installing fonts on the reader's machine, fetching fonts, discarding a brace or box, replacing tags with labels, numbering separately, or trusting a source annotation while ignoring altered visible mathematics cannot satisfy the retained contracts.

**Consequences (Accepted)** · `arg:documents:html-mathematics-consequences`

HTML bytes depend on the plan, notation definitions and pins, the MathML adapter and profile, stylesheet, font bytes, notices and canonical serializer. Browser version, operating system, zoom and accessibility software affect the reading and are recorded in observation evidence rather than folded into generation. Copying may produce different serializations across browsers; practical checks record what each actually copies and exposes to accessibility tools. This is not a formal accessibility-conformance claim. A portable Core subset is narrower than every construct a TeX parser accepts; extensions need a real formula and their own evidence. All needed font files remain embedded unmodified with per-file licence evidence, and their full sizes count against the document's artifact bound. No byte budget or font modification is authorized here.

This amends only the HTML reservations named below. ADR 022's forge Markdown envelopes, contexts and strict expansion remain unchanged. The first implementation admits paragraph inline mathematics through a screen-plan fixture with the real coefficient sources, not a published page for the example document. Recovery of that slice does not demonstrate tag links or equation-number recovery, which have no production consumer yet.

The tag presentation above applies only once mathematical text and tags are represented under a later record: it does not qualify ADR 032:5's sentence “Multi-letter text is carried by the identity of a reviewed nullary primitive, never a widened literal or new AST leaf” or ADR 004's closed syntax. The planned text-and-tag representation requires its own record and consumer before admission. A formula containing a tag omits the TeX source annotation in reader HTML; a handle or source label in that annotation would lie outside M055's exact checked visible-tag span. Recovery then compares the typed presentation and destinations directly with the plan. Tag-free formulas retain an annotation equal to their own planned expanded source; it is corroboration, never the sole comparison. Probe composition does not confer production admission.
