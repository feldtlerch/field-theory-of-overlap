# ADR 017: Screen rendering contracts · `rec:adr:017-screen-rendering-contracts`

**Decision (Statement)** · `dec:documents:screen-rendering-contracts`

The paper and explainer are to retain ADR 016's one-source PDF, Markdown and HTML contract: the PDF remains a rendering, HTML is one page per document, and no rendering is corrected by hand (`rec:adr:016-admission-and-native-documents`). This record decides the screen presentation and review obligations within that contract, not a new source authority.

For each declared language, each document is to have two generated Markdown files from that language's one document plan: the reader Markdown must display reader handles naturally in running text and carry no internal label anywhere, including comments and raw source, while the annotated Markdown must carry every label comment used by recovery, each unit's label before the unit and each tag or citation label beside its handle, and supply the origin evidence read by recovery. For English, the files are to be named en.md and en.labels.md respectively in the document's directory under generated/documents/; en.md is to be the document's Markdown to which readers are directed on the forge that hosts the repository, and en.labels.md is to be recovery evidence rather than a reading surface. Both files must be committed and byte-gated through shared generation and checking, as required for generated artifacts (`rec:adr:006-byte-gated-generation`).

Markdown and HTML mathematics must use fully expanded KaTeX source without document-specific macros, using Unicode characters where the pinned strict renderer accepts them and the pinned command spellings otherwise. ADR 004's primitive spellings and check of every expanded expression against the KaTeX grammar remain the notation contract, and strictness must not be relaxed to admit a screen spelling (`rec:adr:004-notation-ast`). Markdown is to target the Markdown view, with rendered mathematics, of the forge that hosts the repository; what that view accepts must be established by a test against that forge before the Markdown dialect and the mathematics spellings it uses are fixed. The observed refrain-handle presentation fixes one part of that dialect. This record asserts no general forge compatibility, decides neither the rest of that dialect nor those mathematics spellings, and does not decide whether HTML carries the mathematics source for rendering when read or its rendering made at generation.

Section, result, equation and table numbers, and the numbers of the paper's lettered item series (B, R, T and W items), must be computed once in the shared document plan and agree in every rendering. A paper passage quoted in the explainer must link to its destination in every rendering, including PDF, through ADR 016's quotation-use; a linked refrain must show its short reader handle beneath it as the refrain macros of the paper and explainer (`\refrain`, `\paperrefrain`) print it, right-aligned in small type beneath the passage, with each screen rendering presenting it the same way except that Markdown on the repository's forge presents the handle at body size (`rec:adr:016-admission-and-native-documents`). This retains one shared text and one destination rather than a separately authored quotation.

On 2026-11-18, the repository's forge rendered a plain right-aligned refrain handle at body size and did not retain markup for plain small type. PDF and HTML present the handle in small type, where their renderers control that presentation. Every rendering uses the shared text and public destination, and each changed rendering receives independent screen acceptance.

Screen bibliographies must contain the same works and citations as the PDF while allowing a form suited to the medium: every cited key must resolve to the same work and the sets of bibliography entries must be equal, without requiring text, ordering or punctuation to match the PDF. This record does not decide the screen bibliography's form. Where a part is not yet converted, a screen rendering must show a placeholder message without a link; such a rendering cannot satisfy ADR 016's complete-document release gate (`rec:adr:016-admission-and-native-documents`). These placeholders do not replace the required links of converted quotations and references.

HTML must embed every font it needs for prose, monospace and mathematics, unmodified, with each file's applicable licence texts and notices; embedding must wait for recorded licence evidence for each file. Markdown must carry no fonts. This record chooses no font, grants no font permission and decides neither a byte budget nor a different packaging policy when the required evidence is unavailable.

Every rendering must print the audit's precisely bounded coverage statement, derived from the coverage declaration rather than authored independently for each medium (`rec:adr:002-status-and-coverage`). Document conversion must not enlarge the audit, as ADR 016 requires (`rec:adr:016-admission-and-native-documents`). Practical accessibility checks must be made and recorded, without claiming a formal conformance level; this record does not fix which checks are made.

A change that alters a rendered page or screen must receive recorded review before it is retained: a reviewer independent of the change's author must examine page images and rendered screens and judge correctness and appearance against a prepared acceptance sheet. ADR 016's acceptance sentence, “Routine page and screen review may be appointed, approval of theory changes stays with the project's owner, every bound self-description passage is to carry a named renewal acceptor, and the author of a change never accepts it” (`rec:adr:016-admission-and-native-documents`), permits this review without requiring it; this record requires it, and the appointment of a reviewer remains acceptance evidence. The evidence procedure in tools/paper/README.md identifies baseline and candidate hashes, the changed and adjoining physical pages, byte and raw-text comparisons, exact source bytes, destinations and links, and by path and hash every generated fragment or screen rendering a change produces; the review evidence is to add images of those pages and the rendered screens, including both Markdown files and HTML once they are generated. The reviewer must inspect those images and rendered screens, follow links, and record acceptance or required revision with reviewed hashes, page and screen coverage, findings and evidence references. Approval of theory changes must remain with the project's owner, and changed bound passage bytes still require their named renewal acceptance; automated success alone is not acceptance.

**Reasons (Why)** · `arg:documents:screen-rendering-reasons`

- Separate reader and annotated Markdown gives raw-source readers a surface free of internal identities while preserving recovery evidence without a second authored document or a separate origin file.
- Shared expanded notation preserves one mathematical expression across media; strict pinned spellings avoid silent renderer substitutions, while a real forge test keeps compatibility claims within observed behaviour.
- Numbers computed once and quotations linked to their owning destination preserve the identity of what readers discuss across documents and media; the handle beneath a refrain makes that destination recognisable without inserting machinery into its prose. Subscript, superscript, code and keycap markup change the meaning of plain handle text, and heading markup changes the document outline, so none substitutes for plain small type on the forge.
- Bibliographic identity depends on cited works and entry membership, not medium-specific punctuation. Unlinked placeholders expose missing conversion without offering a destination that does not yet exist or implying document completeness.
- Embedded fonts make HTML's appearance independent of installed fonts; retaining unmodified files and their actual licence evidence makes that packaging reviewable. Markdown's presentation belongs to its viewing environment.
- A shared bounded coverage statement separates document completeness from mathematical evidence. Recorded practical accessibility checks provide inspectable findings without an unsupported conformance claim.
- Reproduction proves bytes, not correctness or appearance. Independent image and screen review provides that separate judgment, with an acceptance sheet bounding the review and theory approval remaining distinct.

**Declined (Alternatives)** · `arg:documents:screen-rendering-declined`

Labels hidden only by HTML comments still expose internal identities in raw reader Markdown. Dropping those comments without an annotated artifact discards recovery evidence; independently maintained variants create drift. Document-specific mathematics macros and relaxed strictness conceal differences between renderers; assuming the forge accepts a spelling substitutes expectation for evidence. Separately numbered renderings and unlinked quotations break cross-medium references. Requiring PDF bibliography text on screen constrains presentation without strengthening work identity. Linking an unconverted placeholder misrepresents what can be read. Depending on installed HTML fonts makes appearance contingent on the reader's system, and embedding without per-file licence evidence has no established permission. Claiming formal accessibility conformance or wider audit coverage from document conversion confuses different evidence obligations. An author's own acceptance or automated success cannot supply independent visual judgment.

**Consequences (Accepted)** · `arg:documents:screen-rendering-consequences`

This record partially supersedes ADR 003's Decision clause “rendered Markdown displays tags naturally in running text and carries labels in HTML comments at their sites” for the reader file: the reader file must still display tags naturally in running text but contain no internal label, even in a comment, while the annotated file keeps the whole clause and with it the comment-bearing origin evidence (`rec:adr:003-tags-bound-to-labels`). ADR 003's reason “Labels hide in the rendered Markdown because they are the machine-facing layer: present in the file so tooling reads the same addressable surface from the rendered document as from the source, invisible to the reader because they are machinery, not text.” now holds for the annotated file. ADR 003's other clauses are kept, among them unique live handles at reader citations, bound-label consumers, permanent binding, terminal retirement, namespace collision refusal and exact unknown/retired refusals, subject to ADR 016's existing handle-coverage and audit-independent-addressing supersessions.

ADR 016 retains that policy, “Permanent binding, terminal retirement, exact unknown/retired refusals, unique live handles at reader citations and the existing Markdown label-comment policy remain”, and lets it stand on a stated condition: “No other decision record is superseded: the per-target display bodies of the statement-unit decision and the label comments of the tag decision stand until a later decision names the clause it changes” (`rec:adr:016-admission-and-native-documents`). This record is that later decision: ADR 016's first sentence no longer retains label comments in the reader file, its second sentence is fulfilled rather than reversed, and their other retained clauses stand. ADR 016's other clauses, including quotation-use, independent acceptance, source conversion, release gates and bounded audit coverage, are kept. ADR 004's closed notation, pinned spellings, derived tiers and expression checking, ADR 005's unit and per-target display contracts, and ADR 006's deterministic committed artifacts and shared byte gate are kept. This record does not decide display authoring changes, handle lifetime changes, document declarations or full-model audit obligations.

Document emission and recovery must implement the two Markdown roles together; neither file may be corrected independently of its plan, and recovery must read the annotated file. Until emission implements both roles, the existing en.md carries the annotated form. Shared numbering, citation resolution and entry-set equality, strict notation, placeholder gaps, per-file font evidence, coverage and practical accessibility findings must be carried into implementation and acceptance evidence. The forge test must precede fixing the Markdown dialect and mathematics spellings, and font evidence must precede embedding. Independent review must identify its actual artifact coverage and verdict before a changed rendering is retained. These are prospective obligations, not claims of implemented consumers, acquired licences, completed review or enforced rules; no registered rule's state changes through this record.
