# ADR 015: Open questions are records · `rec:adr:015-open-questions`

**Decision (Statement)** · `dec:questions:open-question-records`

An open question is a question about the theory, or about how this repository represents, checks or presents the theory, that the repository's own content leaves unsettled, on which some statement the repository publishes depends (the statement posts it, is scoped by it, or holds only conditionally on it), and whose settlement would be a change to repository content that can be described in advance, even when that change may never come. Each one is a record in the strict store `registry/open-questions.toml`: a label of kind `open`, which only the store mints; a short title; a concern from the closed set theory, model, documents and machinery, naming what kind of change settles it; the question as one interrogative sentence; typed references to what it is about; one sentence saying in advance what would settle it, including a settlement that only refutation can reach; optional typed references to the statements it blocks and the open records it rests on; and a state from the closed set open, settled, succeeded and withdrawn.

Every closed state is terminal and carries its content: a settlement names the repository objects that settle the question and states the answer, a succession names the open records or graph nodes that carry the question on, and a withdrawal states why the question was ill-posed. A question asked again after it closed is a new record that names the closed one. A typed reference names exactly one domain (a graph node, a rule, a unit, a Markdown-minted record, a paper label, a repository file or another open record) and resolves only there; graph nodes and rules resolve to compiled identities. A record carries no person, date, priority, owner or schedule, and has one English text; a document that presents a question in another language does so in a unit that cites the record.

A candidate goes to the first home that fits it: a gap that is one value on a status axis of one graph object is status data (`rec:adr:002-status-and-coverage`); a check whose statement and scope are settled and that waits only for data or a consumer is a deferred rule (`rec:adr:010-validation-rules`); work whose outcome is known, and on which no published statement waits, is a task outside the repository; a capability or defect of another project, or a discussion, is an issue on a forge; a cost chosen permanently with a decision is that decision's accepted consequence. Only what remains, and on which a published statement depends, is a record. An axiom is assumed and priced, not asked, and stays graph data even where a document lists it among its debts.

Rules M066 to M072 guard the form: closed vocabularies and closures that cannot exist without their content (structural); strict store admission with label form, order and uniqueness and single-sentence texts; the kind reserved to the store and checked against the joint mint inventory; every reference resolved in its own domain; acyclic lifecycle relations with typed closures; and the register `generated/open-questions.md`, which one writer generates and checks under a byte gate (`rec:adr:006-byte-gated-generation`), with every count generated from the store. The paper reference kind exists only while the paper-scoped tag store does (`rec:adr:014-paper-pair`): when the graph gains the node a paper tag names and the paper row is removed, a record still naming that paper label is refused, so it moves to the node reference in the same change. The paper's debts table stays authored under the pair's statement-unit exception; M072 registers its generation from the records the paper cites, deferred until the appendices are statement units.

**Reasons (Why)** · `arg:questions:reasons`

- The open questions a repository posts are part of what it publishes. Held only in prose they cannot be counted, resolved against what they concern, or kept in step with what settles them, and a hand-kept list beside the authority is the drift class the byte gates exist to remove.
- A strict TOML store with closed Rust vocabularies applies the serialization discipline (`rec:adr:011-strict-serialization`) and the closure argument (`rec:adr:001-closed-typed-graph`) to the record's fields, states and reference kinds. Record labels are deliberately not compiled identities: the store grows and settles often, and the admission friction that is the right review point for theory objects is the wrong one for questions about them.
- Terminal states that carry their content make closing a question an act of repository content: only typed references carry authority, and a person or a date cannot be one.
- Succession instead of narrowing in place keeps every cited label meaning what it meant, as retirement does for graph identities.
- The register is a checking inventory for maintainers and auditors, like the rule register, so it names records and subjects by label and prints a paper tag beside a paper object's label. Reader documents see tags (`rec:adr:003-tags-bound-to-labels`); a record gains a documentary tag when a reader document first cites it. The register contains no mint span and no parenthesised label span, so no label harvest reads it as a mint or a citation.

**Declined (Alternatives)** · `arg:questions:declined`

Questions as graph nodes: most questions concern rules, documents or machinery that have no node, the four status axes mean nothing for a question, and every question would need a compiled identity and a theory tag. Records as labelled Markdown: fields and states would be closed only through a bespoke parser, references would be prose that no admission resolves, and the register could not be generated from a source that is already its own presentation. A Rust register like the rule register: every record would change an enumeration and the tests that freeze its size, and question prose reviews worse as string literals. Status vocabulary alone: the questions documents post as open are not axis values, and questions about the system have no node to carry them. Generating the debts table now: it would change printed bytes the paper's byte gate accepts and add machinery to the bounded typesetting layer, and a checker that parses the authored table against the store would need a reader of authored TeX prose that the repository does not have and should not grow for a table that will be generated.

**Consequences (Accepted)** · `arg:questions:consequences`

Status data and records stay independent: an open status axis does not require a record and a record does not require an open status, so neither restates the other. Only textual duplicates are refused; whether two differently worded records ask one question is review's judgement, helped by the register's subject index. Markdown citations still resolve in the Markdown mint domain only, so a decision record mentions a record with a doubled span, and a unit cannot cite a record until records join the unit citation domain together with their first documentary tags. The register states what the store holds and never claims to list every open question of the theory; further records enter as the graph extraction admits their subjects, so their references name graph nodes from the start. Terminality, label permanence and the rule that a record is never removed are held by review of the store and register diffs; no rule compares a revision with its predecessor. Every edit of the store is followed by regenerating the register with `cargo test -p ftoo_codegen --locked -- --ignored regenerate_open_question_register`, and the ordinary test battery refuses a register that differs from its regenerated bytes.
